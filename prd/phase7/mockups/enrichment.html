Recommendation

E2, with E1’s tray grafted into its rail footer.

The tab’s hardest problem is not laying out results — it is that the tab has six states (never run, staged, running, answered, silent, timed out) and most visits will find several of them at once. E2 is the only candidate where all six are the same object: a rail row. Nothing queried yet is nine dashed rows rather than an empty state to apologise for; a running module is a row with a progress bar; a timeout is a row with a clock, which is structurally incapable of reading as total failure because the eight rows around it are unchanged. It is also the only one that does not change shape between 3 modules and 30, which matters because the module list is whatever misp-modules happens to advertise.

What it is missing is E1’s tray. The OPSEC and quota argument is the reason this tab exists as a design problem at all, and a rail footer that only says “Run 3 selected” throws it away. The graft is small: E2’s rail already has the footer, and the tray is a cost line plus a sentence.

E4 has the best single idea on the page — provenance chips, so three modules returning the same hostname reads as corroboration rather than as three duplicate rows. It is worth building later as E2’s “All results” pane, where it costs one extra view rather than the whole tab’s architecture. E3 is the right answer to a question nobody has asked yet: it needs a run-history table that does not exist, and until enrichment is actually queued rather than run inside the request, a ledger of runs is a ledger of one row.

What MISP cannot supply today

Every candidate needs the first three. They are one small table, and they are the actual cost of this tab — the layouts above are the cheap part.

  • No last-run timestamp, anywhere. Module is useTable = false. Nothing records that a module was run against a value, an attribute or an event. Every “Ran today” chip, every staleness reading and the whole since last run delta need a new store keyed by value and module.
  • No memory of a dismissal. The per-element checkboxes in resolved_misp_format.ctp live in the DOM of one modal. Re-running a module re-proposes everything you rejected last time, which is exactly what the delta is supposed to prevent.
  • No cost or quota metadata. Module introspection carries name, mispattributes, meta.description, meta.module-type and meta.config — and nothing about rate limits, credits or whether a module leaves the building. Every quota and third-party marker in these mockups is a curated map MISP would have to own, or a new meta field upstream in misp-modules.
  • No progress inside a module. A module is one POST /query with Plugin.Enrichment_timeout (10 s; Cortex 120 s). Progress can only ever be n of m modules finished — never a percentage within one. The mockups draw it that way; a determinate bar per module would be a lie.
  • Enrichment is not queued. The interactive path runs synchronously inside the HTTP request, and Event::enrichmentRouter returns before its background branch is reached. Only POST /attributes/enrich queues a job. A tab that runs eight modules serially at 10 s each needs the background path fixed first, whichever candidate wins.
  • “Add to event” has no obvious target. MISP enrichment is scoped to one event (handleModuleResults($id)). This value sits in 7, so the target has to be chosen. E3 makes that an explicit select; the others need one on the action.
  • The module list is not cached. Module::getModules() does a live GET /modules on every render with a hardcoded one-second timeout. If misp-modules is unreachable this tab knows nothing at all — not even which modules exist — so a service-down state is required and is not the same as “nothing queried yet”. Each candidate carries the reachability line.
  • Cortex is a second list. Separate family, separate service, port 9000, 120 s timeout, its own auth. No MISP view merges it with Enrichment today — they render two different icons. The picker here merges them and marks the family, which is a decision, not a given.
  • Two smaller things. mispattributes.output is advertised by every module and read by nothing in MISP, so a card cannot say what a module would return without a one-line fix. And Badges/type.ctp renders the attribute-type badge with border border-dark, which vanishes on the dark ground — these mockups use a theme-aware copy.
