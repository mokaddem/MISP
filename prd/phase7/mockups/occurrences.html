Occurrences — four candidates

Ten occurrences of 185.234.219.24, in seven events, from four organisations — six of which this user is allowed to see. The Overview tab already previews this table, so the four candidates disagree about the only thing that makes it a tab: where the filters live, and what the primary unit is — a row, a facet, an event, or a single occurrence.

O1 O2 O3 O4
O1 One dense table at full width: every column, every filter in a bar above it, and the bulk bar docked to the bottom edge.
Optimises for
Reading rows against each other. Twelve columns in the order the Overview preview already uses, so the eye carries over from the tab it just left, and the three columns the preview drops are marked + in the header. The summary strip states the shape of the set in one line, and every number in it is a filter.
Gives up
The shape of the set beyond that one line. A count sits nowhere near the control that would apply it, so “which organisation contributes most” costs a filter round-trip. At 1576px the last columns sit behind the table container’s own horizontal scroll — never the page’s.
At scale
1,847: server-side pagination, 25 a page; the summary counts come from the query, not the page; select-all becomes “all 1,847 matching rows” and the confirmation names rows, events and organisations. 21,904: the same, but the org and tag selects have to become searchable (tom-select is already in the kit) and the summary drops per-type counts. Zero: three separate states — no occurrence you can see, no row matching these filters (filter note + Clear), and everything hidden by ACL.
Data
Rows: Attribute::fetchAttributes in the shape the Overview panel already gets, through index_table with the same field renderers plus sort keys and paginatorOptions. Filters: named params on ValuesController::viewOccurrences, each mapping to a condition fetchAttributes already accepts (deleted included). Bulk bar: multi_select_toolbar, with propose-edit, set-to_ids, set-distribution and add-to-collection as custom_actions. MISP cannot supply a cross-event bulk write: every action here fans out per attribute, and one selection can mix rows the user may edit with rows they may only propose against.
Size
S — one panel, one endpoint, no new primitive.

O3 The table folded along its strongest key: occurrences grouped into the events that carry them, with per-group actions and a ghost group for what ACL hides.
Optimises for
The question a value page is usually opened with — how many separate reports is this, and whose. Event, organisation, published state and distribution leave the row and become the group header, so a row is only what varies inside a group and every column left is a column the preview showed. The event hidden by ACL is a dashed group in the list, not a footnote.
Gives up
Comparison across groups and a stable column grid — two collapsed groups put their rows at different vertical offsets, so scanning one column down the page stops working. And an event is a poor unit for a value carried by hundreds of them.
At scale
1,847: every group collapsed on arrival, the group list paginated (~120 event groups), counts in the headers; “Expand all” disables past 50 groups. 21,904: grouping by event is useless at ~2,000 groups, so the default grouping switches to Organisation — 4 to 40 groups — and event becomes the second level inside it. Zero: no groups, one empty card; the ghost group still renders if the reason is ACL rather than absence.
Data
The same fetch as O1, folded in PHP: Event.id, Event.Orgc or Object.id as the key. Per-group actions are the bulk fan-out scoped to one event, which is the only scope MISP’s per-event ACL check answers cleanly — the strongest argument for this shape. MISP cannot supply the ghost group’s detail: the count of hidden occurrences is knowable (it is the same difference the ACL note already prints), the event ids behind it are not, so the ghost may name a number and never a row.

How they compare

CandidatePrimary unitWhere the filters live Where selection livesReads best when Falls down whenSize
O1 Full ledger The row A bar above the table, plus a summary strip of counts Docked to the bottom edge of the panel The analyst is comparing occurrences against each other and already knows which cut they want The question is about the set rather than the rows — every count costs a round-trip S
O2 Faceted rail The facet A permanent rail, every filter carrying its count Docked to the top of the table, under the header Arrival. The rail answers “who, how, under what distribution” before a row is read The counts have to be honest at 1,847 rows — that needs an endpoint MISP does not have M
O3 Grouped by event The event (or org, or object) A compact bar, with the grouping key as a segmented control Per group in the header, plus the docked bar for the page The value sits in a handful of events and the question is “how many separate reports is this” Hundreds of events: the grouping key has to change under the reader or the page becomes a list of headers M
O4 List and detail The occurrence Collapsed into a Filters dropdown over the list In the list, bar docked under it One row needs to be understood completely — a proposal, an object context, a disputed to_ids Anything comparative. Six rows, six clicks L

Recommendation

O2, with two grafts. The tab has one job the Overview preview cannot do — filter and select — and O2 is the only candidate where that is legible in the first second without reading a row: the rail is the filter set and the summary at the same time, and it is the only place on the page where the ACL truncation stops being a footnote and becomes a number the reader can compare (the banner says ip-dst 7, the rail says 4). Graft O1’s bottom-docked bulk bar onto it — a bar pinned under the panel header pushes the table down every time a row is ticked, which is exactly when the reader is looking at rows — and graft O4’s proposal detail in as a row expander, since a shadow attribute is a diff and a diff has never fitted in a cell.

If the facet-count endpoint is judged not worth building, ship O1 unchanged: it is the S-sized candidate, it needs nothing MISP does not already have, and its summary strip carries the same counts one line at a time. O3 is the better design for this particular value — ten occurrences in seven events is exactly the shape grouping flatters, and its dashed ghost group is the most honest ACL treatment of the four — but it is the candidate that changes behaviour most at scale, and the tab has to work for the Cloudflare-shaped values too. O4 is a panel, not a tab; its detail pane is worth stealing and its list is not worth the width.

What MISP cannot supply today, in one place. Per-facet counts over an ACL-scoped attribute set (O2). A cross-event bulk write, and any confirmation that expresses a selection mixing rows the user may edit with rows they may only propose against (all four). The event ids behind the ACL-hidden occurrences — only the count is knowable (O3). A pending proposal on any of the four demo values: the fixture carries none, so the indicator every candidate is required to show has nothing to render until phase 8 extends it (O4 most). And first_seen / last_seen are optional on attributes and unset on two of these six rows, so a date filter is a filter over a column that is frequently empty — which is why every candidate prints Not set rather than a dash.
