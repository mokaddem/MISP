# Adversarial review — Analyst Profile PRD set

**Date: 2026-09-02. Scope: all twelve files in `prd/analyst-profile/`, 3,447
lines, as of `14e766850`.** The brief was to hunt for inconsistencies between
the documents and for decisions that would make the model unusable on real
data, then propose improvements.

## Verdict

The model is coherent and unusually well-argued. The arithmetic in the
documents checks out — all three ledgers re-summed (84 / 93 / −91 verify to
the unit) and the composition card's regrouping (`10-wiring.md` §2.1) verifies
against the malicious ledger. Every load-bearing factual code claim
spot-checked is true:

- the `enrichmentRouter` dead branch is real — the `return` at `Event.php:7997`
  precedes the `MISP.background_jobs` block, which is unreachable;
- `user_settings.user_id` is `NOT NULL` with the `(user_id, setting)` unique
  key, so it genuinely cannot hold a three-scope object;
- the warninglist category enum is exactly `['false_positive', 'known']`
  (`Warninglist.php`), and `warninglists` has no `uuid` column
  (`INSTALL/MYSQL.sql:1757–1767`);
- `Polynomial::computeScore()` is as quoted, and at `decay_speed = 1` it is
  linear;
- `ValueDisposition::TREATMENTS` has four entries and falls through to
  `NEUTRAL`.

Decisions D1–D9 are internally defensible. What the adversarial pass found
splits into two classes: **calibration assumptions that break on real MISP
data** (§A) and **seven genuine contradictions between phase documents** (§B),
plus smaller drift (§C) and eleven proposed improvements (§D).

The two to fix before anything else: **B1** (it corrupts the upgrade path for
the one profile everyone uses) and **A3 + B5 together** (the shipped default's
conflicted-value story is the feature's demo, and right now it can neither
fire on real data nor be narrated honestly).

## A. Real-data viability threats

### A1. The regression set has no typical value — and the typical value is nearly everything

On a production instance the median value is one occurrence, one org, zero
sightings, no galaxy. Under the shipped weights that is roughly `+7` (one org)
`−7` (galaxy absent) `+6` (no warninglist hit) `±` recency → net ≈ ±10 →
UNKNOWN. All four demo values are heavily-corroborated outliers, and
`03-signals.md` §7.1 calibrates the default against them exclusively.

Consequence: the Verdict tab goes live and ~95% of real pages say UNKNOWN
with a scattering of small grey numbers. That may be the honest answer, but it
is currently an *accident* of calibration, not a decision — and it is the
first thing a user will report as "the feature doesn't work". The acceptance
set needs a value representing the production median, with the intended
verdict stated (→ D9).

*Resolved 2026-09-03 — agreed. The regression set gains the median case
(seeded as an ordinary value, not a fifth fixture demo); the deliberate
outcome is UNKNOWN under `suspicious_floor`, and the shipped default carries
the calibration rule that no single-org, sighting-free value reaches
SUSPICIOUS. `03-signals.md` §7.4 (with §7.1, §7.3, §9), `09-editor.md`
§2.1/§5/§7, `01-profile.md` §1.3.*

### A2. `reporting.independent_orgs` measures re-publication, not independence

The largest positive signal in the model. On sharing communities, the same
public OSINT lands via multiple routes: member orgs pulling the same feeds,
partners syncing the same upstream, re-published event copies. Distinct-orgc
counts systematically overstate independence for exactly the well-known IOCs
people look up most.

The profile has `feeds.mirrored`, but that dedupes *feed hits*, not
org-attributed events created from feed content. The fixture itself
demonstrates the problem: it grades **CIRCL and Team-CIRCL as separate
organisations** — two orgs, one institution, contributing half of the +28.
The biggest signal in the model is the one most inflated by real data, and
nothing in any phase addresses event-level echo (→ D4).

*Withdrawn 2026-09-03 — the finding overstated the mechanism. Org identity
is uuid-preserved through sync (`captureOrg` matches by uuid), and
MISP-format feeds carry the event uuid and Orgc, so the same upstream event
converges to one event under one orgc however many routes it arrives by.
The residuals are second-order and already have homes: freetext/CSV feed
re-publication under different orgcs is rare in communities and the value's
feed overlap is `feeds.mirrored`'s job; org families (CIRCL/Team-CIRCL) are
genuinely distinct orgs, and an analyst who wants a known republisher to
count less grades it down in `org_trust`, which scales
`reporting.independent_orgs` per org. Improvement D4 is dropped with it.*

### A3. The warninglist −38 is a landmine on cloud-hosted infrastructure

With no shipped list setting `category` (`00-discovery.md` §5.4, still
unverified), every hit is `false_positive` → −38. Real C2 today lives on
Azure/AWS/Cloudflare/hosting ranges — lists admins commonly enable. A genuine
C2 on an Azure IP takes −38 toward benign, and the `known`-category escalation
that exists precisely for this case **cannot fire** unless the default profile
ships a non-empty `warninglist_category` map.

Which means:

- **"Empty means as before" is false for the one map that matters.** The
  shipped default *must* carry entries, or the conflicted demo value and
  phase 3's exit criterion are unreachable.
- **Those entries are keyed by name** (no uuid on `warninglists`), frozen into
  every fork, and silently lost on upstream rename. `07-reference.md` §3.2
  admits this but underweights that it applies to the *shipped default's own
  map*, not just analyst overrides.

The upstream `misp-warninglists` PR (`07-reference.md` §3.3, "worth someone's
afternoon") is not a nice-to-have; it is close to a prerequisite for the
concept behaving on real data (→ D5).

*Resolved 2026-09-03 — agreed, with a staged fix that keeps the default
profile's map empty ("empty means as before" survives intact). The pass also
verified the corpus finding (0 of 89 upstream lists set `category`, checked
against `~/git/misp-warninglists`) and found a deeper gap:
`Warninglist::__updateList()` does not import the field at all
(`Warninglist.php:394`). **V1**: a hardcoded name→known map,
`app/Lib/Tools/WarninglistCategory.php`, on the `GalaxyColour.php` precedent,
consulted between the profile map and the database — ~22 shared-infrastructure
and scanner lists, chosen by the litmus test "can a competent report naming
this value as malicious be simultaneously true?". **V2**: the upstream
`misp-warninglists` PR (categories + version bumps + CI schema) plus the
one-line core import fix; when both land, the V1 file retires against a
mechanical criterion. The uuid-column idea (improvement D5's second half) is
dropped — upstream lists carry no uuid and core matches by name. Recorded in
`07-reference.md` §3.1–§3.3, `04-dispositions.md` §5/§8, `00-discovery.md`
§5.4, `01-profile.md` §3.*

*Built 2026-09-07 — V1 shipped as `app/Lib/Tools/WarninglistCategory.php`
with **25** lists rather than the ~22 estimated, each keyed by the exact
upstream `name` read off `~/git/misp-warninglists` rather than transcribed
from the directory name. The 0-of-89 count was re-read the same day and
holds, and the dev instance confirms it from the other end: all 25 roster
names match a list that is present, and not one carries `known` — so
`WarninglistCategory::retirable()` reports V1 as staying. The escalation
this finding said could not fire now fires on the instance's own rows
(`07-reference.md` §7.9, §7.8).*

### A4. No cost budget on the context build

The verdict needs occurrence tallies, sighting rows, tag and galaxy sets,
warninglist and feed checks — *all* of them, in one request, including for
`viewVerdictCard` on the **Overview** tab, which every value page opens. For
an 8.8.8.8-class value on a large instance (the real one sits in six figures
of events, not the fixture's 137), the distinct-org and sighting aggregations
are exactly the queries the lazy-panel architecture exists to defer.

The corpus's own flux value documents the correlation engine giving up at
21,904 — the verdict engine has no equivalent "sampled / gave up" honest state
and no stated budget. Without one, the feature makes the *cheapest* tab the
most expensive request on the page (→ D6).

*Resolved 2026-09-03 — with a better budget than D6 proposed. Row caps and
wall-clock budgets were rejected on determinism (the page, the simulator and
phase 10's worker must agree; a stopwatch never decides verdict content). The
budget is a tiered evidence-time window: normal values fetch everything;
long-history values fetch row evidence for the last 90 days via a new
`evidence.window` exclusion (profile policy, rendered in `not_counted`,
linked to the editor); hot values (`over_correlating_values`) have the
row-hungry signals bow out to `nodata`, the flux precedent. Aggregates —
staleness clock, reporting breadth, continuity — are whole-history always,
declared per signal implementation. `03-signals.md` §2.3 and §9,
`05-exclusions.md` §3/§3.1, `06-staleness.md` §3.3, `01-profile.md` §3.*

### A5. The admiralty mapping misreads its own scale

`07-reference.md` §2.3 maps `F: 0.25`. In the Admiralty System, **F is
"reliability cannot be judged"** — the semantic equivalent of `unrated`, which
the same table maps to 1.00. E ("unreliable") is the bottom; F is "no basis".
The document's argument for admiralty grades is that *"a scale with published
semantics is defensible"* — so the mapping has to honor those semantics. As
shipped, grading an org F (a neutral statement) quarters its evidence (→ D7).

*Resolved 2026-09-03 — confirmed against the shipped taxonomy itself, which
settled it in numbers: `admiralty-scale:source-reliability` carries
`numerical_value` `a=100, b=75, c=50, d=25, e=0, f=50, g=0` — f equals c, the
neutral midpoint, and there is a seventh grade the PRD's A–F scale omitted
entirely: `g`, "Deliberately deceptive". The corrected default is `F: 1.00`
(= C = unrated), `E: 0.25` (floor, not zero — unreliable still means
sometimes right), and `G: 0.00`, zeroing a deceptive org's evidence in both
directions. `07-reference.md` §2.2/§2.3, verification item 4.*

*Built 2026-09-07 — the corrected scale ships in `default-v1.json` as
`reference.org_trust_scale`, so it is data an analyst can move rather than a
constant. Two things the resolution did not foresee. Verification item 4's
`F` case is only observable on a value whose reporting row is **below its
cap** — on the dev instance's widest value, `D` and `F` produce the same
number as unrated because the row is saturated (`07-reference.md` §7.1). And
`E`'s floor does not, on its own, prevent the sign flip the finding was
worried about: `sightings.false_positive`'s extra-organisation term takes
`Σ factor − 1`, which a single `E`-graded filer makes negative, so the term
is clamped at zero (§7.2).*

### A6. Staleness is monotone toward benign — silence promotes values to definite BENIGN

The threat-signed accumulator can only push toward a pole, never toward
uncertainty. `expired: −18` correctly pulls a stale MALICIOUS down — but on a
value sitting at net −50 (inconclusive-benign, UNKNOWN), 180 days of *nobody
looking at it* adds −18 → −68 → crosses `benign_floor` → **definite BENIGN**.
Absence of reporting becomes affirmative benign evidence strong enough to
cross a `definite` band on its own.

Meanwhile a stale BENIGN at −91 gets *stronger* (−109) as its evidence ages —
the opposite of what `06-staleness.md` §5's own "strong evidence, 400 days
old" paragraph argues. The section already routes staleness into confidence;
the score-side contribution needs to argue toward *zero*, not toward benign
(→ D3).

*Resolved 2026-09-03 — and further than D3 proposed: staleness is
**verdict-relative in both states**, not just when expired. Fresh strengthens
whatever the rest of the ledger says, expired argues against it, zero rest is
silent; `points` become magnitudes with the sign computed. The stronger form
was chosen because the fixture itself behaves that way (the benign value's
lifecycle row is −16, supporting benign) and because threat-signed freshness
had its own absurdity: confirming 8.8.8.8 yesterday pushed it out of BENIGN.
`06-staleness.md` §3.2 and §6, `03-signals.md` §2 (the documented exception),
`01-profile.md` §3/§5.2. D11 later subsumed the rule into the relevance axis,
where it holds by construction — `12-assessment.md` §2.2.*

## B. Internal inconsistencies between the documents

### B1. `version` is three things, and they collide

- `02-store.md` §4 uses `version` as the upstream match key
  (`shipped.version > existing.version` → overwrite).
- `09-editor.md` §4.1 increments it on **any** parameters change — and the
  default *is* site-admin-editable.
- `11-restsearch.md` §2.2 uses the same column as the cache discriminator.

So: a site admin tunes the default (version 1→2→5); upstream ships version 3;
the update never applies — or upstream ships version 6 and silently clobbers
the admin's edits. One column, three contracts. Needs `version` (upstream)
split from `revision` (local edit counter, the cache key) (→ D1).

*Resolved 2026-09-03 — the split landed in `02-store.md` §2: a `revision`
column, bumped on any `parameters` change including an upstream overwrite;
`version` moved only by `updateDefaults()`. Upstream-overwrites-local-edits
is now the stated rule, with its honest state (a moved revision makes the
overwrite detectable and logged). `09-editor.md` §4.1 reworded;
`11-restsearch.md` §4.2 already keyed on revision.*

### B2. `direction` has two definitions

`03-signals.md` §2: `direction = sign(row) == sign(total) ? 'with' :
'against'`. `04-dispositions.md` §5.1 (escalation to BENIGN over a +84
ledger): *"every positive row becomes `against`"*. Under 03's formula they
render `with` — sign(row) matches sign(total). The formula must derive from
the *disposition's polarity*, not the total's sign; as written, phase 2 and
phase 3 compute different pages.

*Resolved 2026-09-03 — dissolved by the re-anchoring (`12-assessment.md`
§2.4, `04-dispositions.md` §2): the ledger is anchored to the lean's polarity
at assembly and `direction` is the anchored row's own sign, with no total and
no escalation special-case. Escalations no longer override a score-derived
disposition, so the flipping case no longer exists.*

### B3. The tug bar's `unresolved` bucket is underivable

The conflicted fixture renders `malicious 71, benign 66, unresolved 12`.
`04-dispositions.md` §2 defines unresolved as "points that counted for neither
side" — but the engine has exactly three outcomes (fired-signed, silent,
not_counted) and every fired row is positive or negative. No mechanism
anywhere produces a third signed bucket. Either define it (and break "every
point is a ledger row") or retire the segment in phase 9's fixture pass
(→ D8).

*Reshaped 2026-09-03 by D11 (`12-assessment.md` §4), then settled in the
phase 3 rework: the tug renders the two one-sided threat-signed sums —
support against dispute — and the `unresolved` segment retires in phase 9's
fixture pass (`04-dispositions.md` §5).*

### B4. Excluded-to-empty vs fires-on-absence

`05-exclusions.md` verification 5 demands that when exclusions remove every
sighting, `sightings.volume_recency` is *silent*. `03-signals.md` §4.2's rule
says absence fires whenever an absence key is present in `points` — and
`none_recent: −4` is one. Both documents are right about their own case; the
signal contract needs the distinction **"absent because excluded ≠ absent"**,
and `$context` must carry the excluded counts so an implementation can tell.

*Resolved 2026-09-03 — the distinction is in the signal contract:
`03-signals.md` §4.2, "absent because excluded is not absent". `$context`
carries per-fact excluded counts; an exclusion-emptied input goes to
`not_counted` where the `policy` entry explains it, and absence keys fire
only on genuine absence.*

### B5. The verdict curves have no derivation story — and the flagship narrative is arithmetically unreachable

No phase specifies how the 90-day score history is computed. Replaying the
engine at 90 historical dates is 90× the cost of A4, and historical
warninglist membership is not stored at all.

Worse: the benign value's `curves_note` (called *"the most consequential
sentence in the corpus"*) claims the page said SUSPICIOUS before the
2025-06-24 listing and BENIGN after, *same evidence*. The listing flip is
worth 44 points (`+6 no_hit → −38 hit`). SUSPICIOUS requires net ≥ +40; BENIGN
requires net ≤ −65 — a ≥105-point swing from a 44-point signal. Remove the
−38 from the benign ledger and add +6: net −47 → **UNKNOWN, not SUSPICIOUS**.
The showcase story cannot happen under the specified bands with anything like
the specified weights.

Phase 9's copy table does not list `curves_note`'s narrative as copy in
scope — it should, and the curves panel needs either an as-of replay
specification or a retreat to plotting only what is replayable
(sighting/report history plus the TTL runway) (→ D11).

*Partially resolved 2026-09-03 — the D11 reframe makes the 2025-06-24
narrative reachable: the step is a **lean flip** (the resolver list gaining
the value takes rule 3's precedence, `04-dispositions.md` §3), not a
105-point score swing, so the story survives re-worded rather than retracted.
Still open: how the curves panel derives any historical series at all — the
as-of replay question is unchanged and lands with phase 9.*

### B6. The phase-10 cache key contradicts §5.4

`01-profile.md` §5.5 and `11-restsearch.md` §2.2 both say cache by
`(value, profile)`, *"never `(value, user)`"*. But §5.4's invariant is that
every number is the viewer's — two users on the *same* profile get different
verdicts because of ACL. A `(value, profile)` cache either serves one viewer's
verdict to another (an ACL leak expressed as a score) or is wrong.
`11-restsearch.md` §2.4 flags per-analyst results as open, but the cache
sentence pretends the key question is settled. The key needs the visibility
dimension — `(value, profile, org)` at minimum, and sharing groups make even
that approximate (→ D10).

*Superseded 2026-09-03: the phase-10 rewrite replaced the cache with a
materialised **instance** verdict set by a background worker
(`11-restsearch.md` §3, decision D10). The stored row is no viewer's verdict,
so the contradiction dissolves; the exposure question it leaves is Q13.*

Related: `10-wiring.md` §2's *"the card and the tab **must** come from one
computation"* is unimplementable as stated — they are separate HTTP requests,
and §5.5 forbids the cache that would span them. Either accept two
computations (they disagree only if evidence changes between requests) or
name the micro-cache and spend the invariant knowingly.

### B7. Threshold absolutism vs an open catalogue

The floors (65/40) are absolute numbers over a sum whose attainable range is
the sum of enabled signals' caps (~130–140 today). Every future catalogue
addition (`analyst.opinion`, `relationships.*` — both explicitly planned)
silently inflates scores against fixed floors, re-grading every value on the
instance without any profile edit. Same story per fork: disable three signals
and your effective malicious bar rises. The editor's band strip
(`09-editor.md` §4) should at least display the attainable range, and
save-time validation should warn when floors exceed it (→ D2).

*Largely dissolved 2026-09-03 by D11: there are no disposition floors for a
growing catalogue to race — lean is categorical. Quality banding remains a
calibration to state, with far lower stakes (a misplaced band miscolours a
gauge; it does not flip MALICIOUS). The editor-strip and save-time-validation
improvements still apply, to quality bands.*

## C. Smaller drift

- `01-profile.md` §3's illustrative JSON says `conflict_min_reports` where
  `04-dispositions.md` uses `conflict_min_each` + `conflict_max_gap`, and
  `dedupe_by: "upstream_source"` where `05-exclusions.md` recommends
  `provider`. Illustrative, but these examples are what people copy.
- `08-enrichment.md` §2's example pairs `cost_posture: local_only` with
  `virustotal` in `auto_run` — the document's own defined conflict state, as
  its default example.
- `04-dispositions.md` §3 rule 1 does not say what happens when *two*
  escalations fire (first match by list order? severity?).
- `09-editor.md` §6's fork "replace your current profile" does not say whether
  replace deletes or disables the old one — under the one-enabled-profile
  invariant it matters.
- **"Analyst Profile" collides with MISP 2.5's existing Analyst Data family**
  (`perm_analyst_data`, `analyst_data_blocklists` — the new table's
  alphabetical neighbour). The grilling considered `user_login_profiles` but
  not this. Not worth reopening D1, but the docs should disclaim it before a
  reviewer asks.
- `09-editor.md` §3's `view/:id` shows a weight "next to the contribution it
  produced on the last value viewed" — "last value viewed" implies a tracking
  store nothing specifies.

*C-series resolutions, 2026-09-03. The `conflict_min_reports` drift dissolved
with D11's new `thresholds`. `dedupe_by` now reads `provider` in both
illustrative JSONs, matching `05-exclusions.md`'s recommendation.
`08-enrichment.md`'s example says `allow_external` and states why, with the
shipped default recorded as `local_only` + empty `auto_run`. Escalation
ordering was settled in the phase 3 rewrite: first match in list order, the
meta line names the decider (`04-dispositions.md` §4). Fork-replace disables
and never deletes, with enable-later running the swap in reverse
(`09-editor.md` §6). The Analyst Data collision is disclaimed where the
naming decision lives (`00-discovery.md` §6): weighed, and the name stands.
"Last value viewed" became the simulator's explicit `?value=` parameter, no
tracking store (`09-editor.md` §3).*

## D. Proposed improvements

1. **Split `version`/`revision`** (fixes B1). `version` matches upstream;
   `revision` bumps on parameter edits and keys the phase-10 cache.
2. **Express floors as fractions of attainable range, materialized to integers
   at save** (fixes B7). Keeps exact-sum, makes profiles robust to catalogue
   growth and forked signal-disabling.
3. **Make staleness argue toward zero** (fixes A6). The expired contribution
   takes the sign opposite the rest of the ledger's sum — still one signed
   integer, exact-sum intact, and it renders honestly as *"expired — argues
   against the standing verdict"*. Fresh can stay threat-positive; expired
   toward benign should go. *Superseded 2026-09-03 by the stronger form
   recorded under A6: fresh is verdict-relative too.*
4. **Add an independence model, not just a feed dedupe** (fixes A2). An
   exclusion or discount for occurrences whose event matches a cached feed
   entry (MISP already has feed correlation data), plus an org-alias map in
   `reference` so CIRCL/Team-CIRCL count once. Same shape as `org_trust`;
   belongs in phase 6.
5. **Make the upstream warninglist-category PR a named prerequisite** of the
   conflicted path (fixes A3), and consider adding a `uuid` column to
   `warninglists` in this feature's own migration — cheap, MISP-consistent,
   and stops the shipped default's map rotting on renames.
6. **Give the engine a budget** (fixes A4). Per-fact row caps with a `sampled`
   honest state in `not_counted`, mirroring the flux value's precedent. State
   it in `03-signals.md` §2.2 so implementations inherit it. *Superseded
   2026-09-03: row caps rejected on determinism; the budget is the tiered
   evidence-time window recorded under A4's resolution.*
7. **Fix the F-grade mapping** (fixes A5): `F: 1.00` (= unrated), `E: 0.25`.
8. **Define or drop `unresolved`** (fixes B3). Simplest: the tug bar is two
   sums, and the third segment retires in phase 9's fixture pass.
9. **Extend the regression set** (fixes A1): a median value (one org, no
   sightings) and a cloud-hosted-C2 value (real reports + a
   false_positive-category hit). Those two are where real instances live, and
   neither is currently tested by anything.
10. **Decide restSearch's scope now, cheaply** (fixes B6). Record in
    `11-restsearch.md` that gating uses the *org's* resolved profile and the
    caller's ACL, cache keyed `(value, profile_uuid, revision, org_id)` — it
    answers §2.4, fixes the key, and keeps pipeline output stable within an
    org. *Superseded 2026-09-03 by a stronger form: D10 materialises the
    instance default profile's verdict via a background worker
    (`11-restsearch.md`), matching the industry's status-flip model.*
11. **Restrict the curves to what is replayable** (fixes B5) — sighting and
    report history plus the TTL runway — and rewrite or retract the
    2025-06-24 narrative in the same pass.

Two more that are hygiene rather than concept:

12. **Promote the audit trail from `09-editor.md`'s out-of-scope to phase 1.**
    `00-discovery.md` §3.2(e) says a profile must be *"versioned in a way that
    is legible after the fact"* or the benign-value story is unexplainable —
    then D5 (no lineage) plus no edit history means nothing in the design can
    reconstruct "the profile's knowledge changed on date X".
    `AuditLogBehavior` on the model is nearly free and is the only thing that
    makes §3.2(e)'s promise true.
13. **Require the signal-id registry to be an allowlist**, not filesystem
    resolution à la `DecayingModel::__include_formula_file...` — the simulator
    scores *user-posted* profile JSON, so ids in that JSON must never touch a
    path. Add a size cap on `parameters` while there (it is `longtext`;
    validation should refuse long before 4 GB).

## E. What was checked and found sound

For completeness — claims verified that a reviewer might otherwise re-check:

- All three ledger sums and the composition regrouping (§ above).
- `resolveFor()`'s single-query resolution and its three null paths
  (`02-store.md` §3.1) — sound, including the disabled-default honest state.
- The trust-weighting round-once rule (`07-reference.md` §2.4) preserves the
  exact-sum invariant; multipliers ≥ 0 cannot flip a signal's sign.
- Exclusions-before-trust ordering (`05-exclusions.md` §4) is stated in both
  documents that need it and they agree.
- The banded/editorial resolution of Q5 (`03-signals.md` §5) — the tabulation
  is decisive; "derived" is genuinely off the table.
- The rejection of `user_settings` as the store, the `int` version-comparison
  fix over `decaying_models`' `varchar`, and the `utf8mb4` choice.
- The escalation/section split (D2) survives adversarial probing: no
  candidate rule was found that both contributes points and forces a
  disposition.
